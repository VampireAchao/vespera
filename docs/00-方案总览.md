# 00 · 方案总览

## 结论先行

**可行。** 而且比"看起来可行"更靠前一步：本仓库已经是一个能跑的骨架——`./dev.sh` 会下载 Paper 26.3、
装好插件、起服、敲一条自检命令确认插件活着。剩下的是内容，不是可行性。

但要说清楚瓶颈在哪里：**不在插件，在内容量与合规。**

| 维度 | 判断 | 依据 |
|---|---|---|
| 技术可行性 | 高 | 八族机制已有现成插件（GPL-3.0，且是本项目作者自己的仓库）；对话/菜单用 1.21.6 起的原版 Dialog，不需要客户端模组 |
| 内容可行性 | 中 | 42 章主线 + 72 章种族线 + 24 条支线 ≈ 33–42 万字，9000 行对话。这是三到五个人年的量 |
| 地图可行性 | 中 | 8 区 × 400–600² + 主城 300²。可用 WorldPainter 出地形、WorldEdit 精修、schem 分包 |
| 合规可行性 | 取决于运营方式 | 私人/受邀测试：低风险。中国大陆公开运营并收费：高风险（版号、未成年人、内容分级） |
| 维护可行性 | 中 | Paper 26.x 每季度一个大版本，Java 25 起步。每次升级是"一周的活"，不是"一天的活" |

## 关键事实（2026-10 核对）

| 项 | 值 | 影响 |
|---|---|---|
| Minecraft Java 版 | 26.3（2026-09-15 发布），要求 Java 25 | 服务器与开发机都要 JDK 25；class file 69 |
| Paper 版本号格式 | `26.3.build.<构建号>-<通道>`，不再是 `1.21.x-R0.1-SNAPSHOT` | pom 里必须钉死构建号，否则每次构建拿到的 API 可能不同 |
| Paper 26.3 通道 | 发布初期为 ALPHA，10 月起有 release 构建 | 钉 `26.3.build.159-beta`；升级走单独一次提交 |
| 原版 Dialog | 1.21.6 加入，Paper 从 1.21.7 起提供 API | 对话选项框**不需要任何插件/资源包**，这是本方案的关键红利 |
| mmSupernaturals | 1.5.1，GPL-3.0，Java 25 / Paper 26.3，`api-version: 26.3` | 八族机制直接可用；已改 Maven 构建，产出 `server/plugins` |
| Citizens | 2.0.44（26.3 build #1），OSL-3.0 | 需要皮肤/走动时才引入；不修改即无 copyleft 义务 |

## 架构：四层，一条单向依赖

```
┌──────────────────────────────────────────────────────────────┐
│  Paper 26.3  ·  Java 25  ·  原版客户端直接加入                  │
├──────────────────────────────────────────────────────────────┤
│  机制层   mmSupernaturals                                     │
│           八族 / 转化祭坛 / 血势 / 日晒 / 水伤 / 悬赏           │
│           ↑ 只读。本插件不写它的任何数值                        │
├──────────────────────────────────────────────────────────────┤
│  叙事层   vespera-plugin（本项目）                             │
│           对话（原生 Dialog）· 旗标与计数 · 校历时钟            │
│           小游戏判定 · NPC 锚点 · 演出 · 自检                   │
├──────────────────────────────────────────────────────────────┤
│  工具层   Citizens（可选）· WorldEdit/WorldGuard（可选）        │
│           LuckPerms（可选）· 全部软依赖，缺谁都能起服            │
├──────────────────────────────────────────────────────────────┤
│  资产层   vespera-world                                       │
│           布置清单（yml）· 结构文件（schem，LFS）· 数据包        │
└──────────────────────────────────────────────────────────────┘

构建期：vespera-dev 负责下载服务端、装插件、同步资产、起服、冒烟
```

四个 Maven 模块与它们的边界：

| 模块 | 认识什么 | 不认识什么 | 为什么这样切 |
|---|---|---|---|
| `vespera-core` | 刻、图、条件、谱面 | Bukkit、文件、网络 | 剧本与判定的正确性不该依赖"能不能起一个服务器" |
| `vespera-plugin` | Bukkit、玩家、世界 | 文件系统布局、地图内容 | 换个部署方式不该改代码 |
| `vespera-world` | 只放资源 | 任何 Java | 美术不该为了改一栋楼去动代码 |
| `vespera-dev` | 进程、下载、目录 | 剧情 | 启动逻辑进版本库，而不是进 IDE 设置 |

## 三层契约：谁能写，谁能读

这是全篇最重要的一张表。设计书里那两条铁律（剧情不得改数值、转化必须玩家亲手完成）
翻译成工程语言，就是下面这张读写矩阵：

| 数据 | 写入者 | 读取者 | 违约的后果 |
|---|---|---|---|
| 种族、血势、转化状态 | mmSupernaturals | 本插件（只读） | 一旦剧情能发血势，"成长"就变成"跑腿换经验"，全篇的疼都消失 |
| 旗标、好感、风纪、暴露、教学日 | 本插件 | 本插件 | 记分板/PDC 两套写法混用会导致存档漂移 |
| 世界时间 | 原版 | 双方 | 时钟插件只报时，不推时间——推时间等于替玩家决定白天黑夜 |
| 方块与地形 | 玩家 / WorldEdit | 双方 | 剧情不得凭空改地形；祭坛必须真实建造 |
| 权限与区域 | LuckPerms / WorldGuard | 全部 | PvP 区与非 PvP 区必须显式，否则八族技能在安全区互杀 |

一句话：**机制层是只读的数据库，叙事层是它上面的应用。应用不改数据库，数据库不知道应用。**

## 为什么不用另外两条路

| 方案 | 为什么不做 |
|---|---|
| 模组服（Forge/NeoForge + 自定义模组） | 需要玩家装客户端。与"原版客户端可加入"直接冲突，且网易/家长两条风险的敞口都更大 |
| 整包服务端（把插件、配置、地图塞进一个发行版） | 升级不可控、体积膨胀、地图改动无法 review。本项目用 Maven 分模块 + `plugins.tsv` 解决同一问题 |

## 分期：每次都完整，不是一次做完

| 阶段 | 内容 | 立项即验证的事 | 估时（人·月） |
|---|---|---|---|
| **P0** 垂直切片 | 钟感测试 + 一个锚点 + 状态与旗标 + 校历时钟 + 自检 | 机制—剧情—分支三者能咬合（**本仓库已做到**） | 0.5 |
| **P1** 一学期 | 24 教学日 + 6 门课的小游戏 + 10 社团 + 代亲系统 | 一个玩家能在学院里过完 12 周不腻 | 6–8 |
| **P2** 八扇门 | 八个转化仪式 + 八族各 9 章 | 八个转化都能由玩家亲手完成，且疼 | 6–8 |
| **P3** 主线 | 42 章 + 5 结局 + 10 副本 | 九种状态的玩家都能进议会 | 10–14 |
| **P4** 世界 | 24 条支线 + 60 无名 NPC + 世界文本 | 支线能开主线的替代解 | 4–6 |

> P0 的验收标准只有一句（沿用设计书）：测试玩家在转化后的第一顿饭，会愣一下。如果他没愣，重做。

## 六个风险与缓解

| 风险 | 触发方式 | 缓解 |
|---|---|---|
| Paper 26.3 还在 beta 通道，API 会变 | 下一次 Paper 构建改了 Dialog 或 registry | pom 钉死构建号；升级单独一次提交；`doctor` 打出版本，出问题先看它 |
| 原版 Dialog 是"屏幕"，挡住走路 | 想做"边走边聊" | 分工：重要选择用 Dialog，路过的一句话用 `tellraw` 可点击文本（见 03 篇） |
| 9000 行对话的变量不一致 | 称谓、种族、好感各写各的 | 变量表先定、再写第一句；`doctor` 统计行数；禁词表扫描（见 04 篇） |
| NPC 皮肤与模型 | 想给 24 位有名 NPC 各一张脸 | 锚点与渲染分离：先零依赖跑通，P2 再接 Citizens；皮肤自己画（版权） |
| 音游判定被延迟吃掉 | 玩家 ping 80ms+ | 判定窗 60/140ms + 延迟补偿 + 练习模式 ×1.5；承认它上限是"节奏提示"（见 03 篇） |
| 内容合规 | 题材本身敏感 + 一张截图外流 | 三道闸默认全关（`content.yml`）+ 文本禁词表 + 私人形态（白名单、不公开、不推广）；详见 `docs/06` |

## 需要甲方拍板的三件事

按设计书的惯例，给选项不给结论：

**A. 运营形态 —— 已定：私人 / 受邀**
白名单、不公开、不推广、不收费，大概率只有作者一个人会进。

这个决定换来的东西比想象中多：版号、实名、防沉迷、家长通道四件事一次性消掉，
`docs/05` 里那六条未成年人措施只剩两条还需要做（内容开关、回避机制）。

但要说清楚它**没有**解决什么：**内容层。** 私人不等于可以直说。敏感线仍然走三道闸门
（默认全关），文本仍然走"不命名、不解释、不描写"。全部写在 `docs/06`。
理由只有一条：真正会出事的时刻不是玩家在线时，是一张截图被发出去时。

**B. 地图形态**
① 单主世界拼合八区（推荐）：玩家能走过去，沉浸感最好；代价是世界边界要做成"被擦掉"的地形。
② 多世界传送门：每区独立世界，加载快、隔离好；代价是"走过去"的实感消失。
③ 混合：主世界放流明陨城 + 三区，其余走传送门。

**C. 对话手感**
① 全 Dialog（统一、漂亮，但每次都挡路）
② Dialog + tellraw 分工（推荐，本仓库按这个写的）
③ 全 tellraw（轻，但不适合长文本与输入）

三件事定了，P1 的排期才能落地。技术上没有一条依赖它们——这也是骨架先行的意义。
