# 01 · 插件与功能整合

## 选型的三条原则

**其一，缺了它服务器还能起。** 除了 Paper 与 mmSupernaturals，其余全是软依赖。
理由很实际：一个人维护的服务器，最怕的不是功能少，是"升个版本全站挂掉、而你不知道是哪一环"。

**其二，能读就不改。** 别人的插件（尤其实 GPL/OSL 的）当黑盒用，只通过公开 API 或事件交互。
一旦 fork 改行为，升级成本从"换个 jar"变成"重新移植一次"。

**其三，宁可自己写两百行。** 任务系统、菜单、小游戏这些"看起来有现成插件"的东西，
在本项目里都与剧情状态强耦合（四层筛选、回避旗标、跨章节判定）。接一个通用任务插件，
最后会变成"在它的 DSL 里重写一遍我们的规则"，而且多一个版本风险源。

## 为什么不用 BetonQuest

BetonQuest 是成熟的对话/任务引擎，功能比我们需要的多。三条不选的理由：

1. **它的对话是"线性 conversation"**，适合"点 A 说 B"。设计书 11.5 要的是四层筛选
   （身份 → 关系 → 状态 → 目击），每层都可能改写同一句话。在它的结构里表达这个，
   等于写四倍的 conversation 再做跳转。
2. **状态在它自己那里。** 好感、风纪、教学日要和学院篇、主线、种族线共享。状态一旦分裂到
   两个系统，跨章节判定就会出现"两边都以为对方记着"。
3. **它是又一个版本风险源。** 26.x 的升级窗口里，我们自己那两千行随时能改，别人的不一定。

反过来说：如果 P3 之后需要"可视化任务编辑器给策划用"，那时再评估也不迟——我们的 YAML 是
可迁移的（节点 + 条件 + 动作，任何引擎都吃这一套）。

## 为什么先不做皮肤

性别系统在设计书里要求"两套皮肤 + classic/slim 切换"。技术上可行，但有三处硬钉子：

| 钉子 | 说明 |
|---|---|
| 皮肤要**签名** | 客户端只认带 Mojang 签名的 `textures` 属性。自建皮肤要么走第三方签名服务（数据出境、隐私政策），要么自己伪造（客户端会拒） |
| 切换要**重载** | 改完 profile 需要客户端重新拉一次皮肤，表现为一次明显的模型跳变；设计书已要求用黑屏转场掩盖，这属于演出工作 |
| 合规上**最容易出事** | 玩家皮肤是这个生态里侵权最密集的地方（盗图、真人照片、他人作品） |

所以顺序是：**P0–P2 只用称谓与文本表达性别**（设计书里 90% 的信息量在这一层），
皮肤留到 P3，且必须满足：只用自制或已授权的皮肤、签名服务有隐私说明、玩家可选择关闭。

## 为什么不做经济

半生存半 RPG 的"RPG"如果靠数值成长，就必须有经济；而经济一旦存在，就会长出三样东西：
刷金、通胀、以及"付费变强"的诱惑。三者都会撞上 EULA 商业条款与家长投诉。

本项目的替代方案是设计书已经写好的那条：**奖励是材料、通路、情报、盟友、图纸。**
玩家之间可以有交易（原版交易即可），但服务器不发行货币、不设商店、不卖任何东西。

## 半生存半 RPG：四条边界

| 边界 | 生存侧 | RPG 侧 | 不许发生的事 |
|---|---|---|---|
| 数值 | 原版饥饿、生命、伤害 | 血势（0–10000，插件所有） | 自建第二套数值（攻击力/防御力/等级） |
| 成长 | 装备、附魔、囤积 | 身份（族）、权限（通行证）、通路（钥匙） | "打怪掉经验"式的线性成长 |
| 死亡 | 掉装备、跑尸 | 回响（死一次掉血势） | 剧情发免死金牌 |
| 世界 | 夜晚刷怪、地形危险 | 区域规则（谁不能进哪、谁在哪儿会被烧） | 用剧情脚本替代世界规则 |

一句话：**RPG 的部分是"你是谁"，不是"你多强"。** 这也正好是设计书的主题。

## 性能预算

| 项 | 目标 | 手段 |
|---|---|---|
| TPS | ≥ 19.5（30 人在线） | 视距 8 / 模拟距离 6；锚点不 tick AI；对话无定时任务 |
| 实体 | 常驻 ≤ 200 | 锚点用 `setAware(false)`；不生成装饰性生物 |
| 区块 | 预生成 8 区 | Chunky，在开放前跑完 |
| 内存 | 4–6 GB | 26.x 默认堆更大，按实际压测调；不要照抄旧教程的 Aikar 参数 |
| 定时任务 | ≤ 3 个常驻 | 时钟一个（1 秒）；其余全部事件驱动 |

三个常驻任务里，时钟是唯一"无论有没有玩家都在跑"的东西。这也是它被写成一秒一次、
只做比较不做计算的原因。
