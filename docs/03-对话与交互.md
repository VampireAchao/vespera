# 03 · 对话与交互

这一篇回答"角色对话选项框怎么做"，顺带回答"为什么不是全都这么做"。

---

## 一、四种做法，四种手感

| 方式 | 长什么样 | 挡不挡路 | 要资源包吗 | 能收输入吗 | 适合什么 |
|---|---|---|---|---|---|
| **原生 Dialog**（1.21.6+） | 一块真界面：标题、正文、按钮、悬停提示 | **挡**（等同打开容器界面） | 不要 | 能：文本框、滑块、勾选、单选 | 重要对话、抉择、报名、考试确认 |
| **`tellraw` 可点击文本** | 聊天栏里的彩色文字，`[选项]` 可点 | 不挡 | 不要 | 不能 | 边走边聊、提示、"要不要看看" |
| **箱子 GUI** | 27/54 格，物品当图标 | 挡 | 不要 | 不能（要靠点物品） | 菜单、图鉴、物品选择 |
| **成书**（written book） | 一本能翻的书 | 挡 | 不要 | 不能 | 信件、账簿、判词——设计书的"冷开场" |

四条都能用原版客户端，都符合本项目的硬约束。区别只在**手感**。

### 决策：三件套分工

| 场景 | 用哪个 | 理由 |
|---|---|---|
| 一段有分量的对话（钟感测试、议会、告白） | **Dialog** | 需要排版、需要悬停补充、需要"回避"按钮显眼 |
| 路过的招呼、环境提示、任务指引 | **tellraw** | 玩家不需要停下来；挡路的东西一多，玩家就不看对话了 |
| 一份文件（推荐信、账簿、判词、学生证） | **成书** | 它本来就是道具，翻页的动作本身就是叙事 |
| 选课、选社团、选便当 | **箱子 GUI** 或 Dialog 的 `singleOption` | 图标比文字快；但要写清楚"这是选课"而不是"这是菜单" |
| 要玩家报上名字 | **Dialog 的 `text` 输入** | 别让玩家猜命令 |

一条判定规则：**玩家此刻应不应该还能走路？**
应该 → `tellraw`。不应该 → Dialog。

## 二、Dialog 能做什么（Paper 26.3 实测）

| 能力 | API | 备注 |
|---|---|---|
| 动态创建 | `Dialog.create(factory -> factory.empty().base(...).type(...))` | 每次打开重建，不缓存 |
| 标题 | `DialogBase.builder(Component)` | |
| 正文 | `.body(List.of(DialogBody.plainMessage(...), DialogBody.item(...)))` | 可混排文字与物品展示 |
| 输入 | `.inputs(List.of(DialogInput.text / bool / singleOption / numberRange))` | 考卷、报名表 |
| 按钮 | `ActionButton.builder(...).tooltip(...).width(...).action(...)` | |
| 动作 | `DialogAction.customClick((view, audience) -> ...)` | 服务端回调，不是执行命令 |
| 对话框类型 | `DialogType.notice / confirmation / multiAction / dialogList` | |
| 关闭 | `Audience#closeDialog()` | 会保留之前的库存界面 |
| 是否暂停 | `DialogBase#pause(false)` | 我们的选择：世界照常走 |

代码形状（`DialogueService` 里就是这么写的）：

```java
Dialog dialog = Dialog.create(factory -> factory.empty()
        .base(DialogBase.builder(Component.text(speaker))
                .body(lines)
                .canCloseWithEscape(true)
                .pause(false)
                .build())
        .type(DialogType.multiAction(buttons).columns(1).build()));
player.showDialog(dialog);
```

按钮的回调里拿得到玩家的输入：

```java
DialogAction.customClick((response, audience) -> {
    if (audience instanceof Player player) {
        String name = response.getText("name");     // 文本框
        boolean agree = response.getBoolean("ok");  // 勾选
        float level = response.getFloat("level");   // 滑块
    }
}, ClickCallback.Options.builder().build());
```

### 五个必须知道的限制

| 限制 | 应对 |
|---|---|
| **它是一块屏幕。** 打开期间玩家不能走、不能打 | 别用它做"路过的一句话"；长对话会让人不耐烦 |
| **一次不要塞太多正文。** 正文超过六七行就要滚，观感变差 | 长段落拆节点，用按钮翻页——"下一页"本身就是节奏 |
| **回调有使用次数与寿命**（默认 1 次 / 12 小时） | 每次打开都重建 Dialog，不复用按钮 |
| **不能在回调里直接开下一个 Dialog** | 下一帧再开（`runTask`），否则客户端先收关闭再收打开，会闪 |
| **ESC 可以关掉** | 对"必须回答"的场景设 `canCloseWithEscape(false)`；但**安全阀场景绝不能这么设** |

最后一条是原则问题：设计书 11.6 说"跳过不是失败"。一个关不掉的对话框，就是把玩家锁在里面。

## 三、四层筛选怎么落到代码

设计书 11.5 要求：同一个人、同一句话，按**身份 → 关系 → 状态 → 目击**四层筛出不同说法。
落到数据上只有一个东西——`when`：

```yaml
nodes:
  tent:
    lines:
      - "「你昨晚没回宿舍。」她没抬头。"
    options:
      - label: "我去天台了。"
        when:
          race: [angel, enderborn]        # 身份层：只有能翻窗的人才有这条路
          min: { aff_cecil: 20 }          # 关系层：好感够了她才问得下去
          flag: [curfew_broken]           # 状态层：你真的违反了门禁
          not: [lied_to_cecil]            # 目击层：她还没抓到你说谎
        goto: confess
```

`Condition` 只认这五个键（`race / flag / not / min / max`），键之间是"且"。
**不提供"或"**：要"或"就写两条选项，读起来更像人话，也更好审。

四个层的顺序不影响结果（都是且），但它决定了**你会先写哪一层**——先写身份，再写关系，
最后写状态与目击。顺序写反了，剧本会变成一堆"如果你之前……那么……"。

## 四、安全阀：`avoid`

设计书要求每处敏感场景右上角有"回避"，选了立刻转场、不惩罚、不锁线。
在数据里它就是一个普通选项，只是带了一个约定旗标：

```yaml
      - label: "（回避）"
        tooltip: "你不必在这里被分出高下。"
        tell: "你说你不舒服，先走了。"
        close: true
        flags: [avoided]
```

代码里还有一个 `DialogueOption.avoid(tell)` 工厂方法，写的是同一件事。
`avoided` 旗标不扣任何数值，但它**会被记住**——后续剧情可以用它换一种推进方式
（"你说你不舒服，先走了" → 改成从别人嘴里听说）。这就是"跳过不是失败"的技术含义：
不惩罚，但要留下痕迹。

配套的三件事（P1 要做）：

| 事 | 做法 |
|---|---|
| 进入前提示 | 屏幕底部一行小字，`actionbar` 三秒 |
| 连续回避两次 | 该场景本局永久不再自动触发（旗标 `avoided_<scene>` 计数 ≥2） |
| 不惩罚 | 回避不扣好感、不扣风纪、不锁线——**写进验收清单** |

## 五、剧本怎么写（八条硬规矩）

这八条直接来自设计书第九章，写成可检查的形式：

| # | 规矩 | 反例 |
|---|---|---|
| 1 | 不报数值 | ~~"你的血势还剩 3400"~~ → "你手背上的青筋暗了一格" |
| 2 | 不提界面 | ~~"打开任务日志"~~ → "贝尔纳塞给你一张纸条" |
| 3 | 不念玩家名 | NPC 用称号：学徒、提灯的人、钟匠的接手人 |
| 4 | 不写系统词 | 服务器、插件、冷却、读档、重生点——一律不出现 |
| 5 | 不解释机制 | 让玩家撞一次，再让 NPC 给现象起名字 |
| 6 | 一句一行 | 每行 ≤ 40 字；长段落拆节点，别靠滚动条 |
| 7 | 颜色克制 | 正文米白，强调色不超过两种 |
| 8 | 敏感场景必须有 `avoid` | 缺了就是缺陷，不是"下一版补" |

**变量先定，再写第一句。** 学院篇有 9000 行对话，称谓变量（`${you}` / `${he_she}`）
定晚了，等于重写。这是设计书 11.4 的工程提醒，值得抄在这里。

## 六、三个容易翻车的地方

**其一，多人同场。** Dialog 是单人界面。三个人同时跟贝尔纳说话，会得到三个互不相干的屏幕。
这不是 bug，是设定：**NPC 一次只跟一个人说话。** 其余人应该看到一句"他在跟别人说话"，
而不是排队。要做"围观"，用 `tellraw` 把台词广播给附近玩家（P2 再评估）。

**其二，断线。** 玩家在对话中途掉线，回来时对话框没了。当前实现是"重新右键，从入口开始"。
P1 要加一个"断点"：把 `(graphId, nodeId)` 写进 PDC，重连时提示"上次说到一半"。
注意：**不要自动弹窗**——玩家可能正被怪追。

**其三，重复触发。** 同一段对话反复右键会反复加好感，这是最常见的刷分漏洞。
P1 的规则：每个节点的 `set` 只在该节点**首次**被走过时生效（记 `visited_<graph>_<node>` 旗标）。
一次性事件用旗标挡，而不是靠"玩家不会那么无聊"。

## 七、为什么不用现成的对话插件

| 插件 | 为什么不 |
|---|---|
| 通用对话插件（DeluxeMenus / DialogWindow 一类） | 它们解决"菜单"，不解决"四层筛选 + 状态写回 + 跨章节条件"。用它们等于把规则翻译成别人的 YAML，再被自己的代码读回来 |
| Citizens 自带的 `text` 对话 | 只能播台词，不能分支、不能写状态 |
| Denizen 脚本 | 能做的都做得到，但一门 DSL 的学习与维护成本，超过写两千行 Java |

反过来说：**如果将来策划要自己写对话而不碰代码**，正确的方向是给我们这套 YAML 配一个
可视化编辑器（节点图 + 条件面板 + 出门前的 `problems()` 自检），而不是换引擎。
数据格式已经是"节点 + 条件 + 动作"，任何引擎都吃这一套——这是留给自己的一条退路。
